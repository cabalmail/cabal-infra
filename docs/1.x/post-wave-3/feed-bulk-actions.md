**PR B: Kit feed writes.** Files: `RSS/RssStore+State.swift`, `RssPendingDrain.swift`, `RssSyncEngine.swift`, both view models.
- `RssSyncEngine.markAllRead(scope:)`, the one helper, used by both view models. Under decision 3 (a), in one PR 0.1 `transaction { }` it applies one tap-time watermark to every subscription in scope and queues one ordinary `mark_all_read` row per subscription, all with the same watermark. Same queue kind as today, so older builds, PR 0.2's import of set-aside files and sqlite-mail-store.md PR 4.5 need nothing new.
- The drain groups consecutive `mark_all_read` rows with one watermark into one step. It compares the group's subscriptions with the local catalog: every subscription sends no scope; exactly one folder's subscriptions, nested folders included (`RssStore.feedIds(in:)`), send `folder_id`; anything else goes per subscription. On a 404, a 5xx or a timeout for a grouped call it sends the group per subscription in the same pass, which is safe because a watermark never moves backwards and the flip of explicit unreads repeats harmlessly. It applies the returned watermark to every subscription in the group.

## Background from the rearchitecture

What the sessions need from the rearchitecture project's records, which are not in the repo. F10, F11, F13, F16 and WS-X3 are from that project's audit 02 (feeds) of 2026-10-02; its repo line numbers were for the code of that date and are left out here.

- **F10, feed mark-all-read: duplicated loops, N sequential server calls.** `FeedItemListViewModel.markAllRead` and `FeedManagementViewModel.markAllRead(scope:)` were the same loop over the subscriptions in scope, each queuing one `mark_all_read` and draining. "For 'All Feeds' with 150 subscriptions that is 150 queue rows and 150 sequential POSTs, although the endpoint accepts `folder_id` or no scope." Mail does the same job in one place, `FolderMarkAllRead.perform`. Confidence high, severity low to medium. The audit recommended one `FeedMarkAllRead.perform(scope:)` (or an engine method) that applies the local watermark to every subscription in scope and queues **one** scoped row.
- **F11, no selection abstraction for cross-media Phase 3.** The cross-media plan's Decision 7 says feed bulk selection "adopts the mail list's selection modes as they are", but mail's selection was then a `Set<UInt32>` with a `UInt32` anchor and range base, `RangeSelectionPolicy` was typed to `UInt32`, and `MessageListView+Selection.swift` (551 lines) was built around the index-addressed `LazyVStack`, while feeds use `RssItem` (a string id) in a `List`. Severity medium: "if Phase 3 starts by copying 550 lines of selection code, the duplication problem doubles". The audit recommended extracting `SelectionModel<ID: Hashable>` (selected set, anchor, range base, cursor, bulk mode) and making `RangeSelectionPolicy` generic, mail adopting it mechanically and feeds with `String`, and keeping the list containers separate. Its mail-versus-feeds table called the separate containers "Fine to differ today" (feeds are smaller, and `List` gives native swipe, keyboard and selection for free) but said they become "a cost at Phase 3 (bulk). Plan the shared selection model first", and the separate swipe actions "Fine to differ while feeds use `List`".
- **WS-X3, generic selection model ahead of cross-media Phase 3.** The audit's workstream for F11: `SelectionModel<ID>` and a generic `RangeSelectionPolicy`, mail migrated as a pure type change with no behaviour change (risk medium to high on the mail side, since its selection code carries many fixed bugs, among them #1768 and #901), and feeds given multi-selection "via native `List(selection: Set<RssItem.ID>)` plus the bulk bar". Its scope for feeds was a new `FeedItemListViewModel+Bulk.swift` and batched `setRead` and `setFavorite` in `RssSyncEngine` ("one enqueue per item already coalesces into ≤100-item calls"). Verification: every existing selection and range test passes unchanged (run with the `CabalmailMac` scheme), new feed bulk tests, and a manual shift-click and command-click on macOS. Wave 2.3 F built the mail half's `SelectionModel`; `RangeSelectionPolicy` was already generic when Wave 2.3 was scoped.
- **F13, search-as-you-type reloads race.** `searchQuery`'s and `filter`'s `didSet` each spawn an unstructured `Task { await reload() }` with no cancellation, so an earlier, slower query can land after a later one and overwrite `items`. Confidence medium (FTS is fast, so the race is rare), severity low. The audit recommended holding the reload `Task` and cancelling the previous one, or driving it with `.task(id: query)` in the view.
- **F16, smaller items** (the ones this plan touches; all severity low). `RssItem` is `Hashable` over its full `contentHtml` and `summaryHtml` and is the `List` selection tag, so `onChange(of: model.items)` compares whole arrays of bodies on every change, and every list row loads its body; confidence high on the mechanism, low on a measurable cost at 100 rows; the suggested fix was to select by `RssItem.ID`, load bodies only for the reader, and precompute the snippet in the store. `refreshPendingMarks` runs one actor hop and one SQL query per visible row after every mutation; one `SELECT feed_id, sort_key FROM pending` would do. `FeedItemDate.relative` builds a `RelativeDateTimeFormatter` per call, per row render. `FeedManagementViewModel.update` is server-first, then store, while `RssSyncEngine.updateSubscription` is store-first and optimistic.
- **Wave 2.3 F, the shared selection model** (from the Wave 2.3 per-window navigation scope doc of 2026-10-08, written against stage at `e64b1a7`). Its item 13: `SelectionModel<ID: Hashable>` (selected set, anchor, range base, cursor, bulk mode), owned per window by the navigator for mail: one for the folder list, cleared when the folder changes, and one for the window's search model; each `MessageListViewModel` reads its own; "Feeds adopt it in cross-media Phase 3." The navigator sits above the layout switch (`@State` on `SignedInRootView`); a fold or an iPad resize rebuilds the tree below it (at `e64b1a7`, the list's view model too), and the selection survives because the navigator holds it. Its test rules: behaviour tests on the navigator and the pure policies, no new source scans, and no scan's expected text or anchors edited without the maintainer's yes. It listed the whole-tree source scans that read every new file: `ColorTokenSourceScanTests`, `ConfirmationDialogRoleTests`, `MenuPickerSourceScanTests`, `SceneAppearanceSourceScanTests`, `AddressMenuTitlePolicyTests`, `CompactBrandMarkSourceScanTests`' `testOnlyTheSharedModifierBuildsTheToolbarItem` (no file with both `ToolbarItem(placement: .principal)` and `CabalmailMark(`) and `SwipeActionContainerSourceScanTests`' `rowCallSites` (`SwipeActionRow(` only in `MessageListView+Selection.swift`).

## Risks and checks

1. **Native `List` multi-select may not behave on iOS.** Check: PR E's spike decides before any building; the fallback stays inside `List`.
2. **A checkbox that opens the reader (#2032's class).** Check: the pure reader rule and its tests.
3. **A grouped All Feeds or folder call may run long.** The API Lambdas stop at 29 s with 128 MB (`terraform/infra/modules/app/modules/call/lambda.tf:283`; `modules/app/locals.tf:449-453`), and the handler queries each feed's explicit unreads. At many feeds this could approach the limit *(inferred, low confidence)*. Check: the throwaway-folder timing in PR B; under 3 (a) the drain falls back to per-feed calls on a timeout.
4. **The folder changes between tap and send.** Under 3 (a), the drain falls back whenever the local catalog no longer matches. A narrow window remains when the server's catalog is newer than this device's: a feed added to the folder elsewhere is marked read up to the tap time, and a feed moved out elsewhere but not yet synced here stays read here. Check: Kit tests pin the fallback; the fragment claims nothing more. Under 3 (b) the window is the whole offline period, and a deleted folder needs the 404 drop.
5. **Downgrades.** Under 3 (a), nothing new: older builds read the rows. Under 3 (b), an older build skips the new row (`RssStore+State.swift:131-140`): the device shows those items read while the server does not until the newer build returns, and item marks queued behind the row can be sent ahead of it, so "mark all read, then mark X unread" can end with X read. A soak downgrade drill passes on exactly that.
6. **Lint ceilings.** `FeedItemListViewModel` and `SceneNavigator` are within about ten lines of 250. Check: new code in its own types; recount before each push.
7. **Platform ratchet.** Check: `python3 scripts/check-platform-conditionals.py` before each push; Session 2 does not start until FU-9 has merged.
8. **Pill row width.** Select beside Order narrows the pills at about 322 pt (#2014). Check: an iPad narrow-column screenshot in PR E.
9. **Chords in the wrong section (#2024).** Check: PR E's iPad chord step.
