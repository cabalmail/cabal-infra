Terms used below. An **umbrella** module: `CabalmailKit` keeps its name and re-exports the new targets with `@_exported import`, so a file that says `import CabalmailKit` still sees everything. A **back-edge**: a reference from a lower layer to a higher one. **`package` access**: visible to other targets in the same Swift package, not to the apps. The **proposal** is the rearchitecture proposal of 2026-10-02: its Kit tier reads "CabalmailKit: no UI, split into targets later", with "Core (models, MIME, wire types; linked by watch and extensions)" beside Networking and Persistence, and it left for later, as a separate project, the item to "split the Kit into Core / Networking / Persistence / Mail / Feeds targets so the watch and extensions link only what they need". **The audit** is audit 03, the 2026-10-02 audit of the Kit; **the targets audit** is audit 05 of the same day. Numbers such as 1.0, 1.6 and 1.7 name the rearchitecture's workstreams: 1.0 moved the app layer into `CabalmailUI`, 1.6 reworked the error model and API, 1.7 added `CabalmailShared`. ## Decisions for the maintainer

The session measures the watch saving before asking (first step of "How to start it") and puts the number into decision 1.

1. **How far: Full, Watch cut, Lint only or None?**
   - Full (**recommended**): eight targets under the `CabalmailKit` umbrella (Core, Networking, Persistence, Mail, Editor, Feeds, Design, WatchCore). The compiler keeps mail, feeds and storage apart, and the watch stops carrying the feed store, SQLite, mail code and every JavaScript file.
   - Watch cut: PRs A to C only; mail, feeds and storage stay in one target.
   - Lint only: no targets. A Python check in `lint.yml` fails a PR that adds a back-edge; the watch is unchanged.
   - None: the proposal's Kit-split item closes as won't do.
   - The payoff is unmeasured. Line counts say the watch would compile about 42 percent of the Kit's source, but the Release link already strips code nothing calls, so the binary saving may be far smaller and mostly the bundled JavaScript (inferred, medium confidence). Rule: if the measured saving is under 20 percent of the watch app, the session recommends Lint only and says why. Default: Full, subject to that rule.
2. **Land PR A and a layering lint now, while the split waits? No (recommended) / Yes.** No: sqlite-mail-store.md's Kit thread gets the target map below as a placement note, and this session reruns the reference scan at its start; PR A absorbs anything new. Yes: a small session ships PR A and the lint now, so a new back-edge fails at review, and the SQLite project keeps the lint green until the compiler takes over. Default: No.
3. **`HostPlatform`: Enum only, Keep by path, or Whole file?**
   - Enum only (**recommended**): the enum's four cases, `current` and `ConfirmationDialogPolicy` move into `CabalmailDesign`. The five layout capabilities (`CabalmailUI/Platform/HostPlatform.swift:34-72`) stay in `CabalmailUI` as an extension, where platform-conditionals.md and the Duo work keep adding to them. The watch's by-path compile ends. Cost: `import CabalmailKit` added to about 9 `CabalmailUI` files and 8 app test files that name these types without importing the Kit.
   - Keep by path: both files stay put and the watch keeps compiling them by path (`apple/project.yml:378-379`, documented at `docs/apple.md:1001-1007`).
   - Whole file: the capabilities become public Kit API, and each new one becomes a Kit PR. Not recommended.
   - Default: Enum only.

## Why

- **The watch links the whole Kit and uses a sliver of it.** `CabalmailWatch` (5 files, 534 lines) uses addresses, the hand-off, `CabalmailError`, `ColorTokens` and one dialog rule, yet depends on the entire package (`apple/project.yml:380-381`). It carries the feed store and SQLite, MIME, ICS, and the one resource bundle that holds the composer's and reader's JavaScript (marked, turndown, Readability; `Package.swift:41-59`). It does not compile the composer itself, which is guarded out on watchOS (`Compose/RichTextEditorController.swift:1-7`), nor Spotlight's live index or MetricKit. The audit called this out (F14: the Kit contains UI and app-specific code, and the watch and extensions pay for it).
- **The Kit holds UI and app code.** SwiftUI colour tokens (`Design/ColorTokens.swift:9`), the WebKit, AppKit and UIKit editor (`Compose/RichTextEditorController.swift:7-13`), and the watch's `@MainActor @Observable` model, which "Lives in the Kit rather than the watch app target so `swift test` can reach it (#1124)" (`Watch/WatchAppModel.swift:33-34`; #1124 is closed).
- **Nothing stops layers from tangling.** A type-reference scan at 50e6022 finds four two-way folder cycles and one layering back-edge, listed below.
- **The watch compiles two `CabalmailUI` files by path** (`project.yml:371-379`), because it cannot link that library. It works and is documented, but a rename breaks only the watch build.

What it is not: the app extensions already link only the Foundation-only `CabalmailShared` (`project.yml:450-451, 518-519, 565-566, 634-635`; device check #1945, closed). The split does not touch them.

The watch's two policy files: 1.7 left them out as "UI policy, not extension constants", and the targets audit wanted them in "a tiny target". ## Background from the rearchitecture

What this plan takes from the rearchitecture's records (the proposal, audits 03 and 05 of 2026-10-02, the 1.0 packaging note and the 1.7 scope doc), which are not in the repo. The audits describe the code as it was on 2026-10-02, before the waves; "Where things stand" above is the state at `50e6022`. Their line numbers are left out, so find the code by name.

- **Audit 03's proposed module structure.** Goal: "dependencies flow one way, extensions link only what they need, and Mail and Feeds share a data foundation." Its sketch: `CabalmailCore` (Foundation only, linkable by the notification extension: the models, including `NavState` and the `Rss*` types, errors, `Configuration`, wire types such as `ApiEnvelope`, `PushEnvelope` and `PushTokenPayload`, `AuthTokens`, `SecureStore` and `KeychainSecureStore`, a `Broadcaster<T>`, logging); `CabalmailNetworking` (on Core: `HTTPTransport`, an `ApiTransport` for request building, the forced 401 refresh and decoding, `AuthService` and Cognito, `SessionInvalidationMonitor`, `ConfigLoader` with a cached config, per-domain API protocols with their URLSession implementations, one `Reachability` per process); `CabalmailPersistence` (on Core: `SQLiteDatabase`, an account-scoped `LocalStore` with migrations and a quarantine policy, a `PendingOperationQueue`, a `BodyBlobStore`); `CabalmailMail` (on Core, Networking and Persistence: a `MailStore` with envelopes in SQLite, a `MailSyncEngine`, flag, move and purge through the queue, send, drafts and outbox, MIME, ICS, `ReplyBuilder`, `MailtoURL`, `RulesValidator`, contact suggestions); `CabalmailFeeds` (on the same three: `RssStore`, `RssSyncEngine`, `ReaderAssets`); `CabalmailPlatform` (Core plus Apple frameworks, not on the watch: the Spotlight indexer, `MetricKitCollector`, `ContactsStore`, `PushEnrichmentStore`); `CabalmailUIKit` (SwiftUI and WebKit, app targets only: `ColorTokens` and its asset catalog, `RichTextEditorController` and `WebAssets`, `Preferences`); `CabalmailSession` (all of the above, app targets: the `SessionManager` or `CabalmailClient` composition root). Consumers: the watch links Core and Networking only, with `WatchAppModel` moved back to the watch target or into a test-reachable `CabalmailWatchSupport` target; the notification extension links Core; `swift test` keeps running everything, with one test target per module.
- **Audit 03 WS-K8, the module split.** Goal: fix F14 with the structure above. Scope: `Package.swift` with several targets and test targets; move the files; make `WatchAppModel` reachable through a small `CabalmailWatchSupport` target; have the notification extension link `CabalmailCore` and delete its hand-mirrored wire types (1.7's `CabalmailShared` has since done that half). "It is best after K5, so that file moves don't fight renames; it can be done incrementally starting with UIKit and Platform extraction." Risk: medium (build configuration, resource bundles, XcodeGen's `project.yml`). Size: M to L. Verify: every target builds (iOS, macOS, visionOS, watchOS, the notification extension, the web extensions), the watch binary shrinks, and `swift test` passes per module.
- **Audit 03's other items named here.** F15: `rss`, `rssStore`, `rssSync`, `spotlightIndexer` and `reachability` were optional only because the memberwise initializer used by tests left them nil, so tests never exercised the send queue or reachability through the client; it recommended "a single designated init that takes every service, with fakes in tests", keeping optionals only where a platform lacks the service. WS-K3 (session lifecycle and a single composition root): a process-wide `SessionManager` owning one `CabalmailClient` per account, `CabalmailClient.shutdown()`, intents and push borrowing the session, removing the test-driven optionals, and a single process-wide `Reachability`. WS-K5 (error model and wire layer): one decode helper, typed error cases, per-domain protocols on a shared `ApiTransport`, `host` bound internally, `Encodable` request bodies, and no `as? RssClient` downcast. WS-K9 (small cleanups): a `Broadcaster<T>`, an `os.Logger` sink, deleting the unused `sentFolder` parameter, de-duplicating the `OutgoingMessage` re-stamping, `NavState` and `ResumeSession` as enums with associated values, and per-scene resume keys.
- **Audit 05's proposed target structure.** It wanted membership to be "a property of the folder and the package, not of `project.yml` lists". In the package: `CabalmailShared` (Foundation only, on all four platforms: App Group IDs, defaults keys, keychain coordinates, `PushTokenPayload`, the extensions' control-domain store), `CabalmailKit` (depending on `CabalmailShared`), an optional `CabalmailWatchCore` ("move Kit/Watch/* out of the core Kit") and `CabalmailUI` (SwiftUI, for iOS, macOS and visionOS). The watch shell would depend on `CabalmailShared`, the Kit's WatchCore and `HostPlatform` through a "CabalmailUI-lite" or a tiny `CabalmailPolicies` target, and its WS-E asked to "give the watch its two policy files via a tiny target". Its caveats: as an intermediate step, make `CabalmailUI` an XcodeGen framework target rather than SwiftPM; moving the UI layer out of the app folder would need path updates in about 32 source-scan tests; and "Do not split per feature yet."
- **The 1.0 packaging note (how to package `CabalmailUI`).** It weighed a Swift package against an XcodeGen target. A package must declare its settings, since project settings do not reach packages, and reusing `checkedSettings` would impose warnings-as-errors on app code that had never had it; its tests either stay in the hosted Mac bundle, which must not link a second copy, or move to a package test target, which changes every scan's root; and a second product in the Kit manifest may rename the scheme CI calls (1.7 later confirmed that, hence `CabalmailKit-Package`). The package's main risk was "a second copy of the Kit or UI module in the hosted test process", the failure `c56a904b` recorded (25 broken casts). An XcodeGen target inherits the project's settings and keeps the hosted tests; its risk is how the Kit is linked: if a dynamic framework and the apps both link the static Kit product, the app carries two Kit copies, which a static target linked only by the apps avoids, with the test bundle depending on it without linking (`link: false`). Its recommendation (marked inferred): "a static XcodeGen target for 1.0, then SPM later with the Kit split", with commit 1 a one-file spike proving the link, `@testable`, all four builds and both test bundles, because cloud containers have no Swift toolchain and each try costs a PR run.
- **1.7's lessons from the last package change (its risks 1 to 3, 2026-10-07).** (1) Nothing new should be embedded or signed. A static package product puts its code into each binary that links it, which Apple allows for an app and its extensions alike, but only while the product has no resources, its type stays automatic and no `embed:` is set; a resource bundle or a framework inside an extension is what App Store upload rejects (inferred). PR runs build unsigned, so the Mini checked a signed macOS build: no `Frameworks/` folder or `.bundle` inside any `.appex`, no `CabalmailShared` in `otool -L`, and a clean `codesign --verify --deep --strict`. The first signed iOS upload was the stage push's run. (2) A second product changes the Kit test scheme: Xcode makes a scheme per product plus `CabalmailKit-Package`, and only the `-Package` scheme gets the tests, so 1.7 switched CI and `scripts/build-apple.sh` to it up front, and passed only if the executed test count on macOS and the iOS simulator equalled the merge base's plus the tests it added; the visionOS Kit leg first ran it on the stage push. (3) Tests that had only run on macOS also ran on the iOS simulator (and visionOS on pushes) once they moved into the Kit, so the Mini ran them on both simulators before pushing; any that failed there would become macOS-only with the reason in a comment, not be weakened.

## Risks and checks

1. **A resource lands in the wrong bundle** (the composer never boots; reader mode, colours or acknowledgements fail). Checks: `RichTextEditorBridgeHealthTests` and `AcknowledgementsTests` on the macOS `kit-test` leg; `ColorTokensDriftTests`; simulator runs in B and D, visionOS included; device checks before Promote.
2. **Signing or upload rejects a new bundle.** Checks: the Mini's signing checks in B, C and D; the stage push's TestFlight upload is the final proof; the rollback rule keeps stage moving.
3. **A second module copy.** No target in `project.yml` names both `CabalmailKit` and `CabalmailWatchCore`; the app test bundles keep their `link: false` setup. The app suite's `as? CabalmailError` casts fail loudly if this goes wrong.
4. **`@_exported import` is an underscored attribute.** It is widely used and keeps app imports unchanged, and PR B proves it on the smallest target. Fallback: explicit imports added by script to the 218 app files and 207 app test files.
5. **Tests silently lost in a move.** Check: the executed count on macOS and iOS equals the merge base's in every PR.
6. **Scan blind spots.** A stream site in a new target would escape a scan rooted at `Sources/CabalmailKit`, so decision 4 widens the root to `Sources/`; the decode scan widens to the feed client.
7. **Collisions with other plans.** The Kit freeze covers C and D; git's rename detection helps rebases but does not remove the need.
8. **Builds get slower.** More module boundaries can cost compile time. PR C reports the CI durations; if `kit-test` grows by more than 10 percent, the PR says so.
9. **The payoff is small.** The watch saving is inferred until the first step measures it; decision 1's rule switches to Lint only below 20 percent.
