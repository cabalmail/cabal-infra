## Why

The waves leaned on the app tests as their safety net, and the net has three weak spots.

- **Scans pin text, not behaviour.** 34 test files read Swift source and assert on substrings. Audit 06 warned that an agent "will 'fix' the red test by updating the string to match whatever it just wrote". `CLAUDE.md:92` forbids that, but the count has only grown.
- **Some tests pass for the wrong reason or fail under load.** A fixed sleep before asserting that nothing happened passes on a slow machine whether or not the code is right (06 F8). Local waits of 1 to 4 seconds have been beaten by CI before: the Kit's shared wait notes a loaded runner "once stretched one to 8.8 s against a 2 s ceiling" (`CabalmailKitTestSupport/WaitUntil.swift:4-8`).
- **The paths the next work lives in are checked by hand.** No hosted test holds two windows, and nothing reads `@FocusedValue`, which the menus use (`MessageMenuCommands.swift:27`, `CabalmailApp.swift:101`). The Siri bridge has no tests. No test checks what a view draws.

The keyboard limit is narrower than the waves recorded. Simulator drives can send ⌘-letter chords that SwiftUI commands answer: in PR #1999 (merged) ⌘, opened Settings on the iPad, visionOS and Duo simulators, and in PR #2001 (merged) ⌘A selected all 22 messages. The first press after launch is swallowed, and arrow keys, Esc, Home/End, Page Up/Down and modifier-clicks cannot be sent (#2001, "Not verified"). The older note that synthesized chords never reach SwiftUI (#1929's 2026-10-07 comment) predates #2001, which found the iPad list then had no key handlers at all. #2026 and #2027 came from a real iPad where the simulator had passed ("a synthetic ⌘, sent by the UI-test harness did open Settings", #2026), so that gap is device against simulator.

## Background from the rearchitecture

What this plan uses from audit 06 ("Tests and robustness", one of the seven audits of the Apple code made on 2026-10-02 at the start of the rearchitecture). Its counts are as of 2026-10-02 (31 scan files holding 92 scan test functions; 1,605 unit tests); "Where things stand" above has the counts at 50e6022, and they win where the two differ.

- **How the scans work.** They find the repo through `#filePath`, read production `.swift` files as text, strip `//` comments by splitting each line on `//` (which also truncates `"https://…"` string literals), and assert with `contains("…")` and component counts. Each file carried its own helpers (then `func source(` in 17 files, `func code(in:` in 13 with 12 byte-identical copies, and `func slice(` in 3 with different failure semantics, skip against fail), so their semantics drifted between copies. Nearly every scan says why it exists, in words like "Nothing renders a split/stack/scene/toolbar in a unit test, so this pins the declaration": they are regression pins for bugs in SwiftUI wiring, where the author had no behavioural seam.
- **Two families.** Family A (about 10 files) are corpus-wide rules that walk the source trees, for example `ColorTokenSourceScanTests` (no platform colours), `ConfirmationDialogRoleTests`, `MenuPickerSourceScanTests`, `MacSheetChromeSourceScanTests` and `AsyncStreamTerminationCaptureScanTests`. The audit rated them high value ("These are lint rules"), several with good hygiene (corpus floors, detector self-tests on synthetic snippets, inventories so a new site is not silently exempt), and "Mostly refactor-neutral: they follow code wherever it moves"; their risk is hard-coded probe paths and path-keyed inventories, a one-line edit on a file move. Family B (about 21 files) are declaration pins, exact strings at exact paths, for example `SwipeActionContainerSourceScanTests`, `ReaderColumnFloorSourceScanTests`, `LaunchRestoreSequencingSourceScanTests`, `ComposeWindowOrphanSourceScanTests`, `ToolbarVisibilitySourceScanTests` and the `*WrapSourceScanTests` family. They are medium value as documentation (each names a real shipped bug and its mechanism) and low as verification: a substring match does not prove the behaviour, and the second `ReaderColumnFloor` assertion would pass for any line containing `measuredWidth: measuredWidth`. They block legitimate refactors (a renamed property, an extracted subview, a split file), and "The realistic failure mode with AI agents is worse than the block: an agent will 'fix' the red test by updating the string to match whatever it just wrote. The test then pins the new text, and the invariant is quietly lost."
- **What the audit recommended for the scans.** Re-express family A as SwiftLint `custom_rules` where a regex is enough; otherwise build one shared `SourceCorpus` test helper with a real comment- and string-aware tokenizer instead of copies of the naive split. For family B, one by one: where a behavioural seam exists or can cheaply be added, replace the pin with a behaviour test; where the behaviour lives only inside SwiftUI and UIKit (split column widths, scene activation, toolbar overflow), move the check to a SimDrive or XCUITest smoke and keep the pin, tagged as a wiring pin. Change every `XCTSkip` on a missing anchor to `XCTFail`, and tell agents that a failing scan is a signal to re-verify the named issue, never a string to patch. Since then the agent rule became `CLAUDE.md:92` and the skip was fixed (see "Where things stand"); the decision on family B was "Convert as touched" (decision 2).
- **T2, the audit's scan-triage workstream.** Risk: "Medium (it is possible to drop a real invariant)". Verification: "Each removed scan maps to a lint rule, behavioural test or tagged pin; table in PR body".
- **Duplicated doubles and helpers.** Two `FakeRssClient`s, eight HTTP transport doubles, nine or more poll helpers with 1 to 30 second budgets, 38 inline `Configuration` literals and 12 copies of `code(in:)`. The audit recommended one `CabalmailKitTestSupport` library linked by both test bundles, holding the fakes, `waitUntil` with a single 30-second ceiling, and `SourceCorpus`. The app's poll helpers used 1 to 4 second budgets, while the Kit had learned that CI stretched a sub-second drain to 8.8 s and moved to 30 s. It counted temp directories that are never removed as a leak only, not flakiness.
- **F8, fixed sleeps assert absence.** Then in `RulesViewModelTests.swift` (50 to 120 ms) and `SendQueueTests.swift` (300 ms): "racy-by-design; pass when the machine is slow for the wrong reason". Recommendation: inject a clock or debounce hook (`saveDebounce` is already settable), or assert through a deterministic drain ("await the debounce task") instead of sleeping.
- **F15 and T8, debouncers and pollers.** Seven hand-rolled debouncers and eight pollers. The audit recommended extracting a `Debouncer` and a `Poller`, each with an injectable clock, which "makes F8's tests deterministic"; T8, its error-and-resilience workstream, carried both utilities.
- **F14, view logic outside any test seam.** 162 unstructured `Task {}` in views and 27 direct client calls from views. Recommendation: "As views are touched, move client calls into view models or coordinators, so behaviour becomes testable without scans."
- **F9 and S9, iOS-only code.** The app-layer bundle runs on the Mac host, so iOS branches of shared files go untested. The audit recommended an iOS-hosted test target for `#if os(iOS)` view models and intents, and, in its pre-refactor safety-net list (S9), `IntentBridge` tests for cold-start bootstrap and pending-folder routing in the iOS bundle.
- **`AppState()` in tests** (the audit's table of flaky patterns; the point "Not in this plan" cites as 06 F7). Eleven test files construct `AppState`, which builds a `LiveContactsStore()` and calls `UNUserNotificationCenter.current()` from `setInboxUnread`: real system services in unit tests, which work on the Mac host and would not in a hostless bundle.
- **S8, a scripted smoke.** For layout and foldable groundwork the safety-net list proposed "one SimDrive scripted smoke (sign in to stage → open message → compose → rotate/resize) kept as a manual pre-merge check".
- **What the audit counted as good.** Race tests with deterministic gates (`FakeImapClient`'s hold, await and release) "model in-flight interleavings without sleeps"; `FakeImapClient` traps on unexpected calls rather than no-opping, so a wandering code path fails loudly; isolation is mostly right (suite-named defaults, no `UserDefaults.standard` in tests, `NullHTTPTransport` refusing network).

## Risks and checks

1. **Dropping a real invariant while converting a scan** (06 T2, the audit's scan-triage workstream). Check: each deleted scan gets a row in the PR body naming the property, its issue, the new test, and the mutation run that shows the new test failing on the original bug. No deletion rests on a spike that did not prove this.
2. **The spikes fail.** UIKit may not expose the split's state; `@FocusedValue` may not resolve across hosted windows. Check: timeboxes, a written outcome, and decision 3's default (keep the scans).
3. **Hosted layout tests flake on CI.** If the maintainer makes `apple-gate` required (apple-ci-and-build-config.md's decision 1), a flake blocks every Apple merge. Check: 20 local runs before the PR, an execution time allowance per test, waits through `waitUntil`. Rollback: skip the test with a tracked issue; never delete it or edit an anchor.
4. **The "nothing happens within" helper can still pass on a slow machine.** Check: a positive control in each file, and deterministic hooks wherever cheap (A4's first two tools).
5. **The shared helper changes a verdict,** because correct comment stripping sees text the naive split hid. Check: run every scan before and after; a change is reported, not patched.
6. **A6 races the host app's singletons.** Check: the signed-out assertion and `tearDown` resets.
7. **CI load.** Ten PRs at about six macOS jobs each, against five concurrent. Check: one PR at a time, push only when the queue is empty, and B4's dispatch run only when it is idle.
