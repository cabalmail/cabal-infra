## Why

- **CI's compiler is not the one anyone thinks.** Every Apple job of run 38192104714 (the 1.31.0 promotion, image xcode-27-arm64 20261006.0244.1) logs "Xcode is set to 27.1.0 (27A9269)" with `MD_APPLE_SDK_ROOT: /Applications/Xcode_27.1_beta.app`, and so does every Apple run since at least 2026-10-05 (job 111685960334), including the stage and prod uploads (duo-support.md traces it to 2026-09-25). The image also carries 27.0 GA (27A266a, its default) and a 27.2 beta (duo-support.md, from the runner-images README). The comment at `apple.yml:46-54` says `latest-stable` "resolves to the GA build and skips the betas", and the Wave 2 and 3 scope docs assumed the gates ran on 27.0, so a rule like Wave 2.3's "a compile-time check that is false under Xcode 27.0" was never enforced by CI.
- **The gate does not block anything.** PR #1776 added `apple-gate` as "the one stable check name to require" (`apple.yml:25-26`). The Wave 0 pull-request build check work closed with "One thing only you can do: make apple-gate a required check on stage in branch protection." On 2026-10-12 the API returns "Required status checks not enabled" for stage and main. It cannot be required as built: the `pull_request` trigger has the same `paths` filter as the push trigger (`apple.yml:27-30`), and GitHub leaves a path-skipped required check pending, which blocks every non-Apple PR.
- **The 1.1 GB accident can repeat.** On 2026-10-10 a `git add -A apple` committed 29,312 simulator build files from `apple/.dd-sim-27`, `.dd-sim-27-xr`, `.dd-sim-271` and `.derivedData-sim`. The 2026-10-11 Studio cleanup noted "These are not gitignored, so another `git add -A apple` there would repeat the accident". `apple/.gitignore:33` ignores only `.derivedData/`.
- **Duplication and no bounds.** Six jobs repeat checkout, Xcode selection, Homebrew installs, `xcodegen generate` and `sync-vendored.sh`, and the simulator-creation block appears twice (audit 05 F13). No job has `timeout-minutes`, and `app-build` has no inner `gtimeout`. SwiftLint and XcodeGen come unpinned from Homebrew (0.65.1 and 2.46.0 in job 114626873517), so a bottle update can change lint results or the generated project overnight.
- **Every iOS leg picks an arbitrary device.** The legs take `.[0]` of the device types whose names start with "iPhone" (`apple.yml:174-179, 409-414`); the audit called this "arbitrary and not a foldable". If a runtime update listed a foldable first, CI would test on it without anyone choosing that (inferred).
- **Runner capacity is tight.** Job start times on 2026-10-12 suggest the account runs about five macOS jobs at once (inferred; other workflows' Mac jobs were not counted). In stage push run 38151207543 five jobs started within 12 seconds and four waited 1.7 to 7.6 minutes; over 40 runs, queue waits reached 11.7 minutes. An Apple PR holds 7 Mac runners: 6 in `apple.yml` plus `lint.yml`'s `swift` job (`lint.yml:305-308`).
- **Single sources are missing.** `MARKETING_VERSION: "0.6.0"` appears seven times (`project.yml:213, 342, 413, 479, 537, 595, 658`), so local builds report 0.6.0 while CI overrides it from `CHANGELOG.md` (`apple.yml:804, 1218`). Three generated `Info.plist` files are committed. The audit asked for both fixes (05 F9, F12) and the 0.6 hygiene pass left them out as outside its categories. The floors are declared in three places (`project.yml:28-32`, `Package.swift:22-27`, `Tools/SimDrive/project.yml:17-18`); 05 F18 only noted this, so tying them together is this plan's addition.
- **The release dashboard misses fixes.** The 2026-10-05 review of open issues to close found three fixed issues the soak never saw: #1796 had lost its label, #1858 never had one, and PR #1844 mentioned #1809 several times but never with a closing keyword or a fix phrase the dashboard recognises. The hold reads only issues with a lifecycle label (`scripts/release-dashboard.py:137-139, 481-495`) and only fix claims (`:182-185, 460-478`). The gap is live: #1995 is still open although its fix (`c1d88c23`, "(#1995)") shipped in 1.31.0.

## Background from the rearchitecture

What this plan takes from the rearchitecture's records, which are not in the repo. Their own line numbers into repo files predate `50e6022`, so they are left out here; the plan's line numbers above are the ones to re-check.

- **Audit 05 (targets and CI, 2026-10-02).** The findings this plan cites:
  - **F5:** watchOS and visionOS coverage is build-only. The Kit tests never run on watchOS, visionOS skips the WebKit editor suites, no app-layer test runs on visionOS, and the iOS 18, macOS 15, visionOS 2 and watchOS 11 floors are never executed, because the runner has only 27.x runtimes. It recommended adding watchOS to the Kit test matrix and asked whether the floors should rise to what is actually tested (PR F, decision 3).
  - **F9:** stale and contradictory build-config comments, among them `MARKETING_VERSION: "0.6.0"` hard-coded seven times while CI overrides it from `CHANGELOG.md`. It recommended defining `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` once in `Base.xcconfig`: extensions must match their host, which a single definition guarantees (PR C).
  - **F12:** XcodeGen generates every target's `Info.plist`, but only four are gitignored; the `CabalmailMacNotificationService`, `CabalmailWebExtension` and `CabalmailMacWebExtension` plists are committed and rewritten by every `xcodegen generate`, so a properties edit in `project.yml` leaves a dirty tree or a stale copy. It recommended ignoring all generated plists (PR C).
  - **F13:** six jobs repeat checkout, Xcode selection, Homebrew installs, `xcodegen generate` and `sync-vendored.sh`, which therefore runs twice per job (once more as the project's `preGenCommand`), each time building the Safari bundle and running `npm ci`; `kit-test` needs no `xcodegen`, since it tests the Swift package; no job has `timeout-minutes` and `app-build` has no `gtimeout`; the `Package.resolved` cache key is moot. It recommended a `.github/actions/apple-setup` composite and a `.github/scripts/create-sim.sh` (PR B).
  - **F14:** `scripts/build-apple.sh` claims to mirror `apple.yml` but has no watchOS build, no `app-test`, no iOS-hosted tests and Kit tests on macOS only; ideally CI calls the same script, as `linux.yml` calls `cargo xtask ci --step` (PR E).
  - **F15:** every new extension needs a hand-written per-target `Release` signing block, profile secrets, an ExportOptions entry, a version lockstep block and an entitlements file (the per-target signing block exists because SPM resource bundles reject a profile passed on the command line). It recommended XcodeGen `targetTemplates` and an ExportOptions profile map derived from one table (decision 5).
  - **F18 (minor items):** `CabalmailWebExtension/` holds only a plist and entitlements while its Swift lives in `CabalmailMacWebExtension/`, so it suggested a rename; the deployment floors are declared in more than one place (consistent then); and SwiftLint came unpinned from Homebrew in both `lint.yml` and `apple.yml`, so the two gates could run different versions.
  - **Its CI coverage matrix** marked these as run nowhere: Kit tests on watchOS, app-layer tests on visionOS, CodeQL for Swift, the SimDrive UI harness and the deployment-floor runtimes.
  - **Its workstreams WS-B (CI de-duplication and hardening) and WS-H (build-config hygiene)** cover the ground of PR B and PR C. WS-B's check was a green `workflow_dispatch` run on all legs with wall-clock times compared; WS-H's was an `xcodebuild -showBuildSettings` diff before and after regenerating the project, plus one signed `workflow_dispatch` upload.
- **Audit 07 (platform split, 2026-10-02)** on a separate visionOS target: possible, with the same bundle ID for universal purchase, but only worth it to drop the push entitlements from the visionOS leg; "That is a signing optimisation, not an architecture need" (decision 4).
- **Wave 0's 0.6 hygiene pass** left the seven `MARKETING_VERSION` copies, the plist gitignore gaps and CI de-duplication (F9, F12, F13) alone as outside its six categories.
- **Wave 1.7 (`CabalmailShared`, 2026-10-07)** listed Xcode target templates and version lockstep under "Left out". Its question 4 asked whether to rename the Safari extension folders and recommended no: it is naming only, with no defect behind it, it reaches the signing setup, the changelog gate's folder list and `CLAUDE.md`, and it fits better with the target templates a future extension would bring. The maintainer's answer, "No, but let's make sure it's documented" (2026-10-07), led to the folder note in `docs/browser-extension.md` that says the rename waits for templates (decision 5).
- **Wave 3.2 (layout shells, 2026-10-09), its Duo section.** The Studio has Xcode 27.1 beta (27A9269), with an iPhone Duo simulator and the Duo APIs, beside its default Xcode 27.0, "which matches CI". "Gates use 27.0. The 27.1 beta is only for the Duo simulator run, selected for that command alone (`DEVELOPER_DIR`), not with `xcode-select`." A Duo API, if one proved necessary, would go behind a compile-time check that is false under Xcode 27.0, plus `#available`, in a `Platform/` adapter, built with 27.0 before pushing. Its table of the `duo` branch's extras recorded "Deployment target 27" as "Not adopted; stage stays on iOS 18". The premise that 27.0 matched CI is the one this plan found false (decisions 2 and 3).
- **The Studio git cleanup (2026-10-11)** traced the shared checkout's 1.1 GB `.git` to one commit of 2026-10-10, a `git add -A apple` of 29,312 files in `apple/.dd-sim-27`, `.dd-sim-27-xr`, `.dd-sim-271` and `.derivedData-sim`, and removed it with the maintainer's yes. It left one worktree, Wave 3.2's, with those four folders untracked (6.4 GB): "These are not gitignored, so another `git add -A apple` there would repeat the accident" (PR A's `.gitignore`, decision 8).

## Risks and checks

1. **Ticking the setting before PR A** blocks every non-Apple PR. Check: a non-Apple PR pushed after PR A shows the gate green first.
2. **The filter misses an input,** and an Apple-affecting change merges with the gate green. Check: the comment beside the filter names every file `apple.yml`, its scripts and its tests read outside `apple/`, and review compares it with every `run:` and `uses:` path and with what `sync-vendored.sh` and the drift tests read. A contract test in `scripts/tests/`, like `linux/xtask`'s `workflow_contract.rs`, is welcome if it stays small.
3. **The `changes` job fails** (an API error). Check: the gate goes red by design, never green.
4. **Pinned tool downloads fail.** Check: cache by version, and the error names the URL.
5. **The image drops 27A9269 before the 27.1 release build arrives.** Check: Xcode selection fails by name and a one-line PR moves the record; a silent move only warns, so builds keep running.
6. **Beta toolchain and distribution.** Internal TestFlight accepts the 27.1 beta builds today (every upload since at least 2026-10-05 succeeded), but external groups and App Store submission expect a release Xcode (inferred). Check: move to the 27.1 release build before any external group.
7. **Committed plists carry hand edits.** Check: the byte-identical diff before `git rm`.
8. **Raised floors strand a device** (C2 only). Check: the maintainer confirms every device and rig runs a 27 OS before C2.
9. **Two plans build `create-sim.sh`.** Check: the interface in the scope doc and PR B's body; flags kept whichever lands first.
10. **Capacity.** Decision 6 saves one Mac job per Apple PR; PR F adds one per stage push. Price any new leg (Duo, visionOS tests) against about five concurrent Mac jobs.
