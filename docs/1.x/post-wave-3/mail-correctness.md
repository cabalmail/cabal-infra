## Why

Wave 2 built one mail store. `MailMutationService` owns every optimistic write, `MessageShields` (the *shields*) records writes in flight so a refresh or STATUS cannot undo them, `MailEvents` tells every list and reader, and `MailCounts` holds the folder counts. A *take-back* is the service reversing a failed write's change and its count. A refresh's *licence* is the rule for when a fetched top page may prove a loaded row gone. The two soaks since Wave 2 found five places where this design still leaks.

- **#2037, a stale reader.** Reproduced in the Wave 3 soak on the Mac (3 of 3, "Refresh, Mailbox > Refresh and background polls") and the visionOS Mail tab (4 of 4). A 2026-10-08 build behaves the same, so it is not a Wave 3 regression. A removal the app makes moves the selection through `MailEventSelectionPolicy`. A removal a refresh discovers only prunes the row and the caches. Worse, Refresh and Mailbox > Refresh empty the loaded rows before fetching, so they prove nothing gone at all. A fix that hears only the refresh's prune would leave the issue's own Refresh steps failing.
- **#1990, a server 502.** Reproduced against the stage API with a control: 1 call in 400 to 700 failed while another session toggled flags, 0 in more than 1,700 without. imapclient 2.3.1 returns the unsolicited `FETCH (FLAGS ...)` updates Dovecot sends, each keyed by its UID, and `envelope_dict` indexes `ENVELOPE` with no guard. The Wave 2 soak deferred it out of the soak, not out of the backlog (decision 4).
- **#1973, the one write path with a hole.** A notification's Mark as Read and Archive call `client.imapClient` directly. Nothing shields the write, so a refresh or STATUS already in flight can put the row or count back *(inferred in the issue, not reproduced)*. To catch up, the action hard-reloads every open list, which deletes each folder's saved offline list. 2.1 left it out only because `PushRegistrar.swift` belonged to 1.3 and 3.3 (its scope doc: "file an issue for routing them through the service"; see "Background from the rearchitecture"); the 3.1 scope doc called it "a small PR of its own". **It is a prerequisite for sqlite-mail-store.md:** its PR 4.4 makes the service queue a failed write instead of reverting it, and these two writes never pass through the service. PR 4 closes the hole while the app runs. A cold background launch, with no session wired, keeps writing directly because there is no store to tell; that case is PR 4.4's to cover with the durable queue.
- **#1974 and #1977, count drift.** Both were found by reading code during 2.1 and filed rather than widening it. My reading confirms both mechanisms (high confidence); neither has been seen live. #1977 also saves the 0 into the folder's offline counts. sqlite-mail-store.md's PR 4.4 still reverts a server refusal ("a refusal still reverts"), so #1974's ordering bug would outlive the queue. That is why PR 5 is worth doing now.
- **Page Up and Page Down in search.** PR #1986: "The Tester found that Page Up and Page Down are dead in search too ... `pageScroll` needs the folder window's visible-row range, which search has no equivalent for. That is left alone here." The same guard stops them in the pills, which are server searches (high confidence).
- **Sort during search.** PR #1838 turned the sort menu off in a search or pill, because `search_envelopes` returns newest first only and sorting loaded rows on the device reshuffled rows under the viewport. The rearchitecture project's notes on that PR: "He merged without answering the sort-menu question ... there's no issue to file unless he asks".

## Background from the rearchitecture

What this plan uses from the Wave 2.1 scope doc (mail store and mutation service, 2026-10-08), its sections 3 (scope) and 6 (decisions with defaults). 2.1 built the design this plan patches.

- **What 2.1 set out to build.** Mail events replaced `MessageSignals`: one non-lossy fan-out on the store (removed, restored, flags changed, draft replaced, read advance). Each event carries its origin, the main window that started it (`commandWindowID`) or none (compose windows, notification actions). Lists and readers subscribe and match by each row's own ref, so they work on the search surface. Events go synchronously, on the main actor, in the same turn as the write, to subscribers the store holds weakly; a list's view model subscribes for its own life, not in the view's `.task`. One record of pending writes replaced seven pending-state sets, and the store's counts became the one source for the Unread and Flagged pills and the sidebar. `MailMutationService` takes every user write: list single and bulk flag, seen, move, dispose and purge; the drag move (`applyMoveRequest`); the reader's flags, keyword, dispose, move and purge; compose's `\Answered`; Mark All as Read; Empty Trash. For each it records the pending write and posts the event, moves the counts once, makes the wire call, then confirms (records the removal and prunes the caches) or reverts (clears it, posts the reverse event, puts the counts back). Service calls take the caller's client, and the service checks `acceptsCounts(from:)` once, for every count it writes after an answer and every late event.
- **What 2.1 left out.** Notification actions in `PushRegistrar` "keep writing on their own. With the app open, the list catches up at its next refresh, as now." The 2.1 session was to "file an issue for routing them through the service", since `PushRegistrar` was 1.3's and 3.3's file; that issue is #1973. Mark All as Read and Empty Trash keep their one list refresh request, which `FolderMarkAllReadTests` and `CommandHandoffCharacterizationTests` pin. Envelope-cache flag updates for messages no list has loaded wait for SQLite.
- **Default 4, selection** (the rule behind decision 1), verbatim: "A list moves its selection only when its own selection is on the event's row. If the event names a window, only that window advances, per the user's preference; another window drops the row and removes it from its selection, without advancing. With no window named (compose, notifications), each window whose selection is on the row advances, as today. Read advance is always the naming window's alone. The rule is a pure policy type with tests; the view applies its answer." Decision 1's (b) is this rule applied to a notification's Archive; (a) changes it.
- **What was confirmed.** The maintainer confirmed 2.1's decisions 1, 2, 6 and 7 on 2026-10-08 (rows stay in the lists; one store per `AppState`, reset in place; four open bugs folded into 2.1; the tests that pinned the old signals rewritten through the events, never weaker). The rest, default 4 among them, were defaults the 2.1 session followed without an answer.

## Risks and checks

- **Over-eager let-go (PR 2).** The reader must clear only for rows something proves gone. Tests cover a window move, a paging trim and an arrival that pushes the row below the top page.
- **Clearing the reader on iPhone pops back to the list** *(inferred)*. Check it on the iPhone simulator in PR 2 and describe it in the PR.
- **One signal for two readers.** detached-reader-window.md posts `.vanished` at PR 2's removal point. If PR 2 ends up with more than one entry, tell that plan in the PR body.
- **Counts in PR 4.** Guessing "unread" would push a count one too low when the message was already read elsewhere. Moving counts only for messages the app holds, and letting the poll's STATUS settle the rest, never moves a count the wrong way *(design inference, consistent with `MessageShields.unreadBound` and `flaggedBound`; the tests settle it)*.
- **Background budget (PR 4).** Awaiting the store's task adds the offline-cache forgets after a confirmed Archive. It must not outlast the iOS action budget any more than today's direct call does *(unverified; watch it in the maintainer's locked-iPhone check)*.
- **Another account's notification (PR 4).** A stale notification from a previous account names a folder and UID that may be a different message here. Today's direct write already hits that message on the server; PR 4 would also prune its row and move its counts. `forgetOtherAccount` (`PushRegistrar.swift:299-305`) removes delivered notifications at an account switch, so the window is narrow. account-isolation.md's PR D adds the push-account stamp check after PR 4. State this interim exposure in the PR.
- **#1974's double failure.** Easy to get wrong, so its test comes first.
- **#1990's tests fake the parser.** The fake follows imapclient 2.3.1's documented shapes; the stage reproduction is the real check.
- **Release ride-along.** Anything merged while a promotion PR is open ships in that release. #2043 merged on 2026-10-12. Hold PR 4 until release A's promotion PR merges.
- **CI capacity.** About five macOS jobs run at once; never leave two Apple PRs running together, counting the other Now sessions.
