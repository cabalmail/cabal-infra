## Why

- **Mail and feeds behave differently offline.** "Offline, a mail flag fails and reverts with an error, while a feed flag queues with a clock icon" (the feeds audit of 2026-10-02, audit 02 F9: offline mutations behave differently per medium). `MailMutationService` reverts on failure (`MailMutationService.swift:140-160`); feeds queue durably (`RssStore+State.swift:164-171`). The rearchitecture proposal's decision of 2026-10-02, which the maintainer endorsed: "After the waves, as its own project. It brings offline mail search and makes the cross-media flagged view cheap".
- **Rows live in every list, reader and navigator.** 2.1 kept rows in the lists until the SQLite mail store so the table would not be built twice (the maintainer said yes to "rows stay in the lists", 2026-10-08). 2.2's read-write `envelopes` seam "lasts until the SQLite mail store moves them". 2.3 kept resolved `Envelope` values on the navigator. The costs: a fold shows the top of the list until a refresh lands and rows past 250 reload; two windows on a folder fetch its top page twice (2.2's risk 5); a reader keeps a removed message (#2037, open).
- **The file caches collide and scale badly.** Every merge or removal rewrites the folder's whole JSON file (`EnvelopeCache.swift:89-107, 125-145`). Every body write walks the whole bodies directory (`MessageBodyCache.swift:30-35, 85-117`). File names turn `/` and `.` into `_` (`EnvelopeCache.swift:253-260`, `MessageBodyCache.swift:72-77`), so `zzc/qq` and `zzc_qq` share one file (#1871, reproduced on macOS: "One file throughout").
- **One shared directory for every account.** `SessionEnvironment.swift:78-88` returns `Application Support/Cabalmail` with no account part. Sign-out empties it with `try?` at each step (`CabalmailClient+Maintenance.swift:17-29`). A sign-in as another user empties it under a live session (pinned at `SignInCharacterizationTests.swift:366`).
- **Queued feed marks can already be lost.** The feed `pending` table lives inside `rss.sqlite` (`RssStore.swift:469-472`), and `openRecovering` deletes that file when it is corrupt or written by a newer schema (`RssStore.swift:78-87`). A tester who installs an older build after any schema bump loses unsent feed marks.

### Design rules (settled in the first project scope doc, then held)

**Two classes of data.**

| Class | What | If lost |
|---|---|---|
| Cache of server state | envelope rows, message bodies, folder list and counts, the address list, feed catalog and items, the Spotlight index | refetched online; an offline launch right after shows less |
| Irreplaceable | the outbox (unsent mail and attachments), draft buffers (edits newer than the last `/save_draft`), feed `pending` rows, the new mail queue | gone for good |

The feed `pending` rows are irreplaceable but sit inside a cache file that recovery deletes (`RssStore.swift:78-87`). Sign-out deliberately deletes both classes today (`CabalmailClient+Maintenance.swift:17-29`); the Phase 4 list asks whether it should warn first.

1. A cache file may be deleted and rebuilt whenever it is corrupt, written by a newer schema, or older than legacy files beside it. Recovery code never deletes an irreplaceable file: it sets it aside and logs it, as `RecordQuarantine` does.
2. Irreplaceable data never shares a file with a cache. The mail queue gets its own `queue.sqlite`; PR 4.5 moves the feed `pending` rows into it. A read may join the two files on one connection (SQLite's ATTACH). No write relies on one transaction across both files: in WAL mode a crash during such a commit can apply it to one file and not the other (SQLite's ATTACH documentation). A change writes its queue row first, in one transaction in `queue.sqlite`, and what the user sees is derived from the queue (PR 4.3), so #1956's guarantee survives the move.
3. No release moves irreplaceable data and changes a cache layout at once. With decision 4's default, the outbox and drafts never move.
4. Every migration step is idempotent and runs at every launch, not once behind a flag, so an older build that ran in between is absorbed. A legacy-format file beside the new layout means an older build ran: the cache is rebuilt from it (it is newer), and any queued rows in it move into the queue.
5. The queue file evolves additively. It records the oldest schema that may write it; an older build leaves it untouched and its writes revert as they do today. A row of a kind this build doesn't know is left in place, as `PersistedRecord` does.
6. Server changes are additive (00-working-agreements.md, docs/compatibility.md), ship to stage before or with the client, and reach prod one release before a client that relies on them, because a TestFlight build from stage talks to prod. The client replays only when the response says the server checked the precondition.
7. Each phase's last PR updates the Progress table in `docs/1.x/mail-store-plan.md` and the as-built storage and offline section of `docs/apple.md` (CLAUDE.md docs convention).

### Phase 1: The account directory (one release)

**Status:** Not started (2026-10-15).

Kit thread. Hotspots: `SessionManager.swift`, `SessionEnvironment.swift`, `CabalmailClient.swift`, `CabalmailClient+Maintenance.swift`, `SignInCharacterizationTests.swift`.

- **PR 1.1 Account directory.** `Application Support/Cabalmail/accounts/<scope>/`, where `<scope>` is `Preferences.scopeIdentifier`, computed inside the Kit (for example `CabalmailClient.make(…, account:)`), since that function is internal; preferences and files then share one key. By default the envelope, body and folder-state caches open there. The scope doc picks how the client learns its account: passed to `make` (sign-in knows the typed username; restore and `borrowClient` know `lastUsername`), or the caches open when the session is wired. Recommended: the first *(inferred: smaller)*. A directory made by a sign-in that then fails is removed. A process-wide registry gives every client of one account the same store objects, and later one drain lease (PR 4.1).

## Background from the rearchitecture

What this plan takes from the rearchitecture's records (the proposal and audits of 2026-10-02, the Wave 1 to 3 scope docs and two notes), which are not in the repo. The audits describe the code as it was on 2026-10-02, before the waves; "Where things stand" above is the state at `50e6022`. Their line numbers are left out, so find the code by name.

- **The proposal (2026-10-02; the maintainer endorsed its recommendations that day).** Its mail-and-feeds table kept the two persistence engines apart during the waves: "Converge later: mail envelopes into SQLite through the existing wrapper, with one account-scoped root. A separate project, not part of the first waves." For optimistic writes (mail reverted in memory; feeds wrote store-first with a durable queue): "Share one pipeline shape; mail adopts the feeds design over time." Stores announce their own changes, as `EnvelopeCache.changes()` already did. Its target architecture has one per-account mail store (envelopes by `MessageRef`, counts, optimistic writes) shared by every window, above a Kit persistence layer (SQLite, body blobs, a durable pending-operation queue). Its list of later, separate projects opens with moving "mail envelopes into SQLite under one account-scoped storage root with a shared offline operation queue (so mail flag and move work offline like feeds)". Two of its decisions matter here: this project, "After the waves, as its own project. It brings offline mail search and makes the cross-media flagged view cheap"; and the mark-all-read watermark, "Change it" (the Lambda accepts the tap time, a small backward-compatible addition shipped through stage), which decision 9 follows for mail.
- **Audit 03 (the Kit), F3: mail has no repository or sync layer.** The app wrote the envelope and body caches directly, in pairs, from several view models, and mail flag, move and purge had no offline queue; only send did. It recommended a Kit `MailStore` actor that owns both caches and offers intent-level operations doing the network call, the cache update and the change announcement together, with a mail pending-operation queue later on the same pattern feeds use.
- **Audit 03 F12: eight persistence mechanisms with inconsistent layout, scoping, eviction and corruption policy.** Preferences were per account (hashed keys) while every file cache sat in one shared directory wiped at sign-out; the resume record was per install; `RssStore`'s doc said "One SQLite file per account" while `make` put it in the shared directory. Only `MessageBodyCache` had a cap, and its eviction walked the whole body directory on every store. Every `EnvelopeCache` merge, replace or remove re-read and rewrote the folder's whole JSON file. The file-name sanitizer mapped `/`, `.` and `_` to one name, so `A/B`, `A.B` and `A_B` collided. Nothing but the push mirror was in the App Group. Sign-out missed `BimiUrlCache`, `ContactsStore` and `DebugLogStore`. It recommended one foundation: envelopes into SQLite through the existing `SQLiteDatabase` wrapper (incremental updates, FTS for offline search, one migration story) under one account-scoped root, `<AppSupport>/Cabalmail/accounts/<scopeHash>/{mail.sqlite, bodies/, rss.sqlite, drafts/, outbox/}`.
- **Audit 03 F13: offline write queues and retry policy differ per feature.** The HTTP transport retried any request once after a lost connection or timeout, POSTs such as `/send` and `/move_messages` included. Mail send queued in `Outbox` JSON files, with no backoff and a silent drop after 10 attempts. Mail flag, move and purge had no queue and returned the error to the view model. Feed marks queued in the SQLite `pending` table, drained on each local write and app trigger but not on reachability, with no backoff and never given up. Save draft had no queue, by design. It recommended one `PendingOperationQueue` with a persisted operation log, an idempotency key, exponential backoff, a reachability trigger and a dead-letter state, backed by SQLite and used for feed marks, mail send and later mail flag and move. Decision 9 recommends preconditions instead of the keys; decision 6 keeps the outbox out.
- **Audit 03's work streams.** WS-K6 (persistence foundation): an account-scoped root; quarantine instead of delete for undecodable files; schema-versioned Draft and Outbox records; an outbox change stream, dead-letter state and backoff; a body-cache index instead of a directory walk per write; a fixed file-name sanitizer; a one-time migration from `AppSupport/Cabalmail/*` to `accounts/<hash>/*`; verified by "migration tests with fixture directories; corrupt-file quarantine tests; and an upgrade test from the current layout on device". WS-K7 (`MailStore` and `MailSyncEngine`): envelopes into SQLite with FTS, the store owning the cache-coherence logic then spread over the view models, a shared `PendingOperationQueue`, the `MailboxWatcher` poll scheduler under `MailSyncEngine`, and Spotlight following store changes. "Not in this plan" declines the `MailSyncEngine` part.
- **Audit 02 (feeds), F9: offline mutations behave differently per medium.** Mail flag and read changes call the server and revert on failure; feed changes are queued durably and shown with a "queued" clock. Its recommendation: if mail flags gain offline support, reuse the feed queue's design (one row per item and kind, latest intent wins, fences), not its code.
- **Audit 01 (mail), dual-screen groundwork.** The reader's selection was a value copy and "should be a `MessageRef`, resolved through a store, so two panes showing the same message stay consistent and a reader in one pane reflects flag changes made in another". The list model's lifetime was tied to its view. Pollers started per mounted list, so N windows meant N pollers per folder, and a folder-status service with subscriber fan-out would scale to several panes.
- **Audit 06 (tests and robustness): swallowed errors on data paths.** The local draft save, the outbox remove after a successful send (a failed remove re-sends, softened by the server's Message-Id dedupe, #1019), the send queue's drop after its last attempt (a log line only) and the sign-out cache wipe all used `try?` or logged only; of the wipe it said "A failed wipe leaves the previous user's mail on disk." Its T8 item ("No silent loss") asked for a test for each surfaced failure and a transport retry for idempotent methods only. This plan leaves the retry, the outbox and draft-save errors to hardening-web-and-writes.md ("Not in this plan").
- **Wave 1.6** left "SQLite failures as `.storage`" undone: `SQLiteDatabase.Error` leaks from `RssStore` (audit 03 F9), in `RSS/`. PR 0.1 maps it.
- **Wave 2.1 (mail store and mutation service).** The maintainer said yes (2026-10-08) to "rows stay in the lists" and "one store reset in place". 2.1 left "a table of envelopes by ref" to the SQLite mail store, since building it in memory first would build it twice; readers keep their envelope and follow flag events for their ref. It also left "envelope-cache flag updates for messages no list has loaded" to SQLite (PR 2.4), and notification actions writing on their own (#1973). Mark All as Read and Empty Trash keep their one list refresh request, which `FolderMarkAllReadTests` and `CommandHandoffCharacterizationTests` pin.
- **Wave 2.2 (the folder window loader).** Because rows stay in the lists, each STATUS from the shared folder poller still goes to every list's own refresh, and the read-write `envelopes` seam on the list's view model lasts until the SQLite mail store moves the rows. Its risk 5: "Two windows refresh in lockstep from one STATUS, so two top-page fetches go out together" (PR 3.4).
- **Wave 2.3 (the navigator).** `SceneNavigator` holds the window's route as IDs and, beside it, the resolved `Folder`, `Envelope` and `RssItem` values the views still take: "Those stay until a store can resolve refs" (PR 3.5).
- **Wave 3.3 G (the list's place).** Asked to keep the list model alive across a fold or build on the top-row anchor alone, the maintainer chose the anchor ("Answer: anchor only.", 2026-10-09). Under it each list keeps building its own model; after a fold the top of the list shows until the rebuilt list's first refresh lands (the #1664 gate), then it moves to your row; rows past the top 250 reload; "Nothing in `MessageListViewModel*` changes." Holding the model was set aside because during a fold the old and new trees are both alive, so a model shared by both would end up off its poller with its page loads cancelled, and it cost roughly 150 to 250 more lines. The anchor (`ListAnchor`) holds the folder path and the top row's Message-ID, UID and index, and is recorded only for a folder list on the All pill with the default sort. G1's check: on the Duo simulator, fold and unfold with INBOX at about rows 30, 300 and 700; the list comes back at the same row after its refresh, repeat folds don't drift, and scrolling during the refresh wins; on iPad, two windows with the divider dragged.
- **Offline launch notes (2026-10-04, on the Mini, a macOS build of stage).** Offline, the Mail folder list was empty and the pill counts were zero: the envelope snapshot stores no totals and the per-folder counts lived in memory only, though each cached envelope carries its flags, so the cached rows' unread and flagged counts can be computed as a lower bound. Inferred from the code: marking a cached unread row read offline took the Unread pill from 0 to 1 (the optimistic step clamps at 0, then the revert adds 1), and the same path overwrote the app badge. A trap for any fix: "Seeding `totalMessages` from a saved STATUS would also make the list draw placeholder rows it can't load offline. Keep the pill numbers separate from the paging total."
- **Sticky feed order (2026-10).** Its rollout rule, which rule 6 copies: the server PR is promoted to prod before the client PR that uses it merges to stage, because "a TestFlight build from stage talks to prod". Its known limit: an order change made offline isn't queued; if the write fails, the next refresh restores the server's value, and only an offline queue beyond read and flag marks would fix it (PR 4.5).

## Risks and checks

- **Losing irreplaceable data.** Rules 1 to 5 and the drill after every phase. Check after each release: the outbox, a draft, an offline flag and a feed mark survive an upgrade, a downgrade and a return.
- **A store shared by several clients.** Sign-in, standby and MFA clients coexist. The registry gives one store and one drain lease per account; a test opens two clients for one account and checks they see one write and only one drains.
- **Late writes at sign-out.** The #1937 and #1957 shape for mail: close the stores and release the lease, then delete the directory; a write after that recreates a directory the next launch deletes.
- **Stale or harmful replays.** The UIDVALIDITY check stops wrong-message writes, not an old intent; the age limit and latest-change-wins bound it. TestFlight builds write to prod mail, so the kill switch and Discard All are tested in the Phase 4 soak. Review each Phase 4 PR against rule 2 (no transaction across two files).
- **Main-thread cost.** Rows come from an actor; the main-thread table keeps rendering synchronous. Check scroll and open times on the 700-row fold case.
- **Disk growth.** Set a row cap in Phase 2; the body cap stays 200 MB.
- **Scans and pins.** The stream inventory (decision 8), `LaunchRestoreSequencingSourceScanTests` (Phase 3) and the sign-in pin (Phase 1) are asked up front, never edited to pass.
- **Feed schema 7.** If flags-and-cross-media.md's B2.3 lands first, it must keep PR 0.2's set-aside import working for slot rows, and PR 4.5 must move them.
- **File protection.** Keep today's protection class so a notification action can write the queue while the device is locked *(inferred check)*.
